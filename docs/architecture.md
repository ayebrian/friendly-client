# Архитектура

## Направление зависимостей

```
app (composition root)
 ├─ infrastructure → domain + shared/errors
 └─ features → domain + shared
                    shared → domain
```

`domain` — модели и контракт `FriendlyGateway`, без React, HTTP и библиотек.
`infrastructure` — HTTP, проверка ответов Zod, преобразование wire-форматов,
хранилище сессии. `features` — независимые функциональные срезы.
`app` собирает настоящий адаптер, связывает провайдеры и маршруты. Между features нет прямых
импортов: связи устанавливает app. `check:architecture` проверяет эти границы.
Состояние навигации и фильтров локально; серверные данные только в TanStack Query.

## Интерфейс и формы

UI-примитивы генерируются shadcn CLI в `shared/ui` (Radix, preset radix-mira).
`components.json` задаёт пути; алиас `@/` тоже проверяется на границы модулей.
Компоненты используют общую тему Tailwind 4. CSS экранов задаёт расположение,
а интерактивные состояния, клавиатурное управление и ARIA берутся из примитивов.
`shared/feedback.tsx` собирает общие состояния из Alert, Skeleton и Avatar.

Форма входа использует React Hook Form с Zod resolver. Некорректная почта и
неполный код не отправляются в API; ошибки связаны с полем через aria-describedby.
Новые события показывает один Sonner Toaster внутри сессии; выход удаляет
сообщения аккаунта вместе с кешем. Вкладки и меню аккаунта используют Radix.

## Сессия

При каждом входе создаётся новый QueryClient. Выход/401 демонтирует дерево сессии,
отменяет запросы и очищает кеш; другой аккаунт не получает данные предыдущего.

Токен API хранится только в cookie `__Host-friendly-session` (HttpOnly, Secure,
SameSite=Strict, Path=/), которую ставит прокси `/api` (см. ниже). JavaScript страницы
токен не видит. В localStorage (`friendly.session.v2`) лежит только несекретная отметка
`{ id, accessHash }`: она показывает всем вкладкам, какой аккаунт держит cookie. Вкладки
следуют событиям `storage`: вход, выход и 401 в одной вкладке применяются к остальным;
выход или 401 старого аккаунта не стирают аккаунт, вошедший в другой вкладке. Новая
вкладка, клик по push-уведомлению и перезапуск браузера не выходят из аккаунта. Сервер не
ограничивает срок токена; cookie живёт 400 дней (максимум браузеров) и заканчивается
выходом или 401. Если localStorage заблокирован, отметка живёт в памяти документа.

Прежние сборки держали `{ id, token, accessHash }` в sessionStorage вкладки. При первом
запуске новая сборка один раз передаёт такой токен в `POST /api/_session/migrate`; прокси
проверяет его запросом `/users/details2`, ставит cookie, а клиент удаляет читаемую копию.
Отклонённый токен тоже удаляется; при сетевой ошибке копия остаётся до следующей загрузки.
Настоящие токены не попадают в URL, логи и репозиторий. Тестовые данные находятся только в `src/app/fixture-gateway.test-utils.ts`; приложение
не предлагает демо-сессию.

## Уведомления

ActivityProvider смонтирован над всеми маршрутами после входа. Список и badge
используют один снимок кеша. Опрос — каждые 30 секунд в видимой вкладке, также при
возврате фокуса и восстановлении связи. Это работает без PWA и push. Закрытая
страница обновления не получает. Push и WebSocket можно добавить позже как
сигнал invalidate существующего query, без второго хранилища уведомлений.

API не предоставляет известного нам endpoint общего числа непрочитанных.
Адаптер загружает страницы до конца, максимум 20 за цикл. Повторы событий
удаляются; повтор cursor приводит к ошибке. Если достигнут лимит, complete=false,
badge показывает нижнюю границу (`N+`), UI сообщает о неполной истории. Не выдаём
число одной страницы за точный общий счётчик. Полный обход каждый цикл — осознанный
компромисс первого среза; для большой истории нужен отдельный endpoint count или
инкрементальная синхронизация с подтверждённой семантикой порядка событий.

Прочтение оптимистично обновляет тот же кеш. Запросы опроса отменяются и
приостанавливаются на время мутации. Одновременные операции прочтения блокируются.
API вызывает read отдельно для каждого события; при частичной ошибке
восстанавливаются только неуспешные записи. После завершения список сверяется
с сервером. «Прочитать всё» при неполной истории становится «Прочитать загруженные».

Новые события после первичной загрузки дают сообщение внутри окна на другом
маршруте. Начальная история не вызывает поток старых уведомлений. Badge также
отражается в заголовке вкладки. После ошибки обновления старые данные сохраняются
и интерфейс сообщает об ошибке.

## Прокси API (BFF)

API Friendly принимает токен только в заголовках `X-Token`/`X-User-Id` и не поддерживает
cookie. Поэтому все запросы клиента идут на тот же origin, в Cloudflare Pages Function
`functions/api/[[path]].ts`; логика — в `bff/proxy.ts`. `/api/<путь>` пересылается на
`FRIENDLY_API_ORIGIN` (по умолчанию https://api.getfriend.ly) с тем же путём и query.

- `POST /api/auth/login` и `/api/auth/generate`: токен из ответа переносится в cookie,
  клиент получает тело без `token`.
- Остальные запросы получают `X-Token`/`X-User-Id` из cookie, только если клиент назвал
  аккаунт несекретным заголовком `X-User-Id`, совпадающим с cookie. Иначе токен не
  добавляется (картинка `/api/…` из поста не выполняется от имени пользователя); без cookie
  — 401 без обращения к API; cookie другого аккаунта — 409 с `X-Friendly-Session: changed`,
  и вкладка переходит на аккаунт из отметки или завершает сессию.
- 401 API удаляет cookie; успешный `/auth/logout` удаляет cookie, ошибка выхода её сохраняет.
- Пересылаются только `Accept`, `Accept-Language`, `Content-Type`, `X-Locale`, `X-File-Size`,
  `X-Compatible`; cookie, `Authorization`, присланный клиентом `X-Token` и служебные
  заголовки Cloudflare отбрасываются. Тело (в том числе multipart) передаётся потоком,
  статус ответа сохраняется; из ответа берутся только тип, `Content-Disposition`,
  `Content-Language` и `Retry-After`, плюс `Cache-Control: no-store` и `nosniff`.
- Изменяющие запросы (не GET/HEAD) принимаются только с `Origin`, равным origin сайта:
  защита от CSRF в дополнение к SameSite=Strict, включая подмену входа.

Медиа `/files/download/{id}/{accessHash}` — capability URL без авторизации; `<img>` и
`<video>` загружают их прямо из API (`VITE_API_BASE_URL`), не расходуя запросы Functions.
`public/_routes.json` ограничивает Functions путём `/api/*`, статика отдаётся без них.

Компромиссы: XSS больше не может унести токен, но внедрённый скрипт, пока страница
открыта, может отправлять запросы через `/api` от имени пользователя. Все запросы API
проходят через Functions (лимиты запросов и CPU тарифа Cloudflare, тело запроса до 100 MB
на Free/Pro); API видит адреса Cloudflare, а не пользователей, поэтому его лимиты по IP
могут срабатывать на общих адресах.

`npm run dev` и `vite preview` обслуживают `/api/*` тем же кодом (`scripts/bff-dev.ts`),
upstream задаётся `FRIENDLY_API_ORIGIN`. Cookie с `Secure` Chromium и Firefox принимают на
http://localhost и http://127.0.0.1, Safari — нет.

## Сетевой слой

15-секундный timeout, отмена через AbortSignal, ограниченные повторы только
запросов чтения. Мутации автоматически не повторяются. HTTP ошибки преобразуются
в ApiError. Ответы проверяются на границе и преобразуются в доменные модели.
Неизвестные типы activity сохраняются с нейтральным отображением.
Числовые ID проверяются на safe integer: backend описывает 64-битные ID; большие
значения требуют lossless JSON parser и строковых ID, а не тихого округления.
Текст выводится как обычный текст; HTML из публикаций не исполняется.

## Публичные маршруты и приглашения

Главная `/` показывает лендинг; `/login` и `/signup` — вход и регистрацию. После
регистрации без приглашения открываются настройки для привязки почты. После
обычного входа открывается лента или исходный защищённый маршрут.

`/invite#?reference=add%2F…` и старые `/redirect/…` открывают гостевой экран до входа.
Приглашение остаётся в fragment при входе, регистрации и перезагрузке, без отдельного
storage. После авторизации `/invite` показывает подтверждение; `/friends/add`
вызывается только по нажатию. Ссылки и QR создаются на текущем origin через настоящий
API. Кеш друзей обновляется после успешного принятия. Ошибки сети, истёкшие и
собственные приглашения не показывают успех. Уход и выход отменяют операции.

Полный серверный сценарий требует двух настоящих аккаунтов. Проверки клиента
перехватывают HTTP-ответы, используя настоящий сетевой адаптер.

## Визуальное направление после входа

Референс: компактный интерфейс социальной сети с обычным списком событий.
Настроение: простой, рабочий, читаемый.
Палитра: белая рабочая область, холодные нейтральные поверхности, синий акцент для действий.
Шрифты: системный sans-serif для интерфейса; Arial Bold для небольшого названия приложения.
Особенность: непрочитанные видны в навигации, строке и заголовке вкладки браузера.
Без рекламных слоганов, hero-блоков, декоративных карточек и крупных serif-заголовков.

Клавиатурный фокус, семантическая навигация, aria-live, валидация формы,
пустые/ошибочные/загрузочные состояния, цели касания 44px и reduced-motion.
